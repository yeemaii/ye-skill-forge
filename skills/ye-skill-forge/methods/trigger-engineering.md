# 触发工程方法

## 目标

让 skill 在职责内请求上可靠触发，在相邻但职责不同的请求上保持清晰边界。是否属于业务执行或一次调用并不决定退出；业务 Skill 应执行自身职责，Ye 的元职责排除规则不能复制到目标 Skill。触发设计关注用户意图和任务语义，不依赖堆积关键词。

## Description 设计

用简洁结构说明：

1. skill 负责的重复任务；
2. 用户可识别的动作和对象；
3. 必要上下文或输入；
4. 不应触发的近邻任务，以及应改用的工具或 skill。

动作词要具体，例如“审查代码”“生成 API 文档”“根据反馈改进 skill”；“处理”“看看”“代码”通常缺少足够上下文。多语言和同义表达只加入真实用户会使用、且能改变路由的少量变体。

description 应保持可路由的密度，不要把完整案例库、长篇流程或所有关键词塞进 frontmatter。完整样例放在 `evals/`，原则和边界放在 `SKILL.md` 或 `methods/`。

## 案例结构

推荐使用以下字段：

```json
{
  "positive": ["应该触发的请求"],
  "negative": ["不应该触发的请求"],
  "near_neighbor": ["高度相似但职责不同的请求"]
}
```

每个案例最好说明 `expected_route` 和 `reason`。负例不是绝对禁用词；它必须带有足够上下文，避免把合法请求误列为负例。

## 指标口径

在有模型或客户端执行结果时，报告：

- 触发召回率：应触发案例中实际触发的比例；
- 触发精确率：实际触发案例中正确触发的比例；
- 负例拒绝率/特异度：应拒绝案例中实际拒绝的比例；
- 近邻混淆：近邻案例被错误路由到本 skill 的数量和示例。

没有执行预测时，只报告案例数量和 `missing`/`static` 状态，不能把案例存在写成准确率。指标必须同时记录分母、样本来源、执行方式和失败案例。

## 迭代原则

1. 收集误触发、漏触发和近邻混淆的真实案例。
2. 判断是 description、边界、上下文还是上游路由问题。
3. 做最小修改，优先减少歧义，不盲目增加短语。
4. 重跑原案例、正例、负例和近邻例。
5. 根据误触发和漏触发的代价选择严格程度；“宁缺勿滥”只适用于漏触发代价较低的场景。

触发评测必须明确是静态案例检查、模型执行、客户端执行还是人工审查。不同证据类型不得混为一个分数。
