# 领域方法设计

创建 Skill 的交付物不是填满模板，而是让一个正常请求沿正式入口得到可使用的结果。模板和 CLI 只建立结构；领域方法由 Agent 根据用户材料、已有做法和可核查结果补全。

## 先确定用户结果

写清：

- 用户反复要完成的工作和最终结果；
- 用户会提供的输入、必要材料和已有参考；
- 结果依赖的判断、工具、权限和固定协议；
- 什么请求相邻但属于别的职责；
- 怎样从真实产物或用户判断看出完成。

“创建一个 X Skill”是交付形式，不是职责。没有既有失败时，不能凭空编造失败；应记录希望稳定复用的结果或方法。

## 从材料提炼方法

优先读取真正生效的入口、完整参考、脚本、模板、示例和真实产物。对每个候选做法说明：它改变了什么结果，哪些输入和判断使它成立，哪些部分只是案例中的事实、措辞或临时处理。

目标 Skill 只吸收未来正常请求会使用的稳定方法、必要材料和清楚的边界。失败输出、纠正故事、维护记录和一次性项目事实留在报告或项目材料中，不进入活动规则。

如果直接复用代码、模板、示例或素材，记录来源、许可证、采用范围和改动；只学习方法并重新实现时，不把来源变成运行依赖。

## 把做法转成决策

先分类，再提炼：稳定判断写指令；重复且确定的处理写脚本；具体人名、日期、项目事实留在输入或案例；一次性补救先查根因，不直接变成通用规则。

对影响结果的做法写出 `适用条件 -> 判断依据 -> 行动 -> 失败处理 -> 完成证据`。不是每条指令都填五个字段，只补足实际影响判断的部分。

例如“分析要深入”不能稳定改变行为。可以改为“比较各来源对同一主张的支持与反证；有冲突时分别记录依据，不按来源数量投票；没有可核查依据时标为未知”。用冲突来源和缺证据案例检验，避免把一次报告的章节或篇幅固定为所有输入的要求。

先从正常请求推演方法，再用缺失输入、边界和已有成功例检查。自然语言足以表达时不增加配置或脚本；必要交接与失败条件不能仅靠模板标题代替。

## 选择最小实现

自然语言足以表达的判断直接写入 `SKILL.md` 或专用参考。只有重复、确定、手写易错且结果必须一致的处理才写脚本。只有子职责能独立触发或复用时才创建 Skill 家族；固定顺序的相依步骤优先保持一个入口。

先列出完整任务必需的判断、分支、工具、状态和失败恢复，再减少结构。第一版承接约定的完整任务；原型或范围缩减需要用户明确接受，不能用“后续迭代”推迟已知必需能力。一个入口也可以包含复杂方法、条件资源和多阶段脚本。

在创造性或开放判断任务中区分必须满足的事实、边界和质量要求与可自由选择的表达、结构和路径。具体决策只约束影响正确性或用户目标的部分，不把某个成功案例的固定章节、语气或长度升级为全部输入的规则。

模板完成后删除不适用的资源、组合、配置或角色说明，保留必要的失败处理。脚本保留显式 description，Agent 仍应检查其与目标、自然触发和排除项的关系；有问题时改写并说明，不把用户给出的描述当作不可修改。

## 创建后核对

先做结构和信任检查，再沿正式入口运行代表性请求。记录当前源摘要、输入、期望、实际观察、评审方式和版本。结构通过只能证明文件可读；行为证据必须绑定当前源摘要，才能被发布审查使用。

案例要能辨别关键判断，例如有负责人和缺负责人、独立来源和转载、充分证据和冲突证据。主观效果另外使用任务相关的评价或用户反馈，不能仅靠章节、短语和字段存在判断。新任务允许在明确假设下试做，验证失败再修正，不以缺乏历史数据拒绝低风险探索。

核对时改变一个影响判断的输入，观察方法是否应改变：明确更正与未解决冲突不同，转载与独立研究不同，命令成功与原症状恢复不同。按目标选择有区分力的情况，不机械增加边界数量。若规则对两者都只要求“分析并总结”，补足缺少的判断；不要只增加“更深入”或重复警告。按 [案例索引](../examples/README.md) 选择相应设计示范。
