# 改进方法

## 核心原则

- 用户关心的问题优先，但先确认它属于这个 skill 的重复职责。
- 以真实反馈、输入样例和运行结果为依据，不把猜测写成事实。
- 保留已验证的有效行为，只做能解释失败的最小改动。
- 有基线、样本、评测规则和执行方式时才量化效果；否则写成定性目标或“缺少证据”。
- 提案、应用和验证是三个不同状态，不把提案当成已修改，也不把静态检查当成效果提升。

## 收集反馈

优先使用开放式问题：“使用中遇到了什么问题？请给出一个实际输入和结果。”允许用户提供文本、目标目录内的 `@文件`、对话记录、输入/输出样例和期望结果。

反馈记录至少区分：

- 实际请求和上下文；
- 实际结果与期望结果；
- 应保留的有效行为；
- 问题类型：路由、工作流、输出契约、边界、上下文或运行时；
- 未确认的假设和可能缺少的证据。

关键词分类只能做初筛，不能替代对目标 skill、失败案例和相关资源的阅读。

## 生成提案

每项提案包含：观察、根因假设、目标文件、最小修改、应保留行为、验证用例和证据限制。新增功能必须先回答“它是否服务于原有重复任务”；否则应建议新 skill 或保持边界。

用户只请求分析或方案时生成提案；请求改进、修复或已授权维护时继续修改目标，保护用户已有改动，不重复索取本地修改授权。修改后至少重放原始案例和一个近邻负例或回归例；多个相互依赖的改动可以作为一个最小的连贯变更，不强行拆成互相矛盾的微改动。

## 验证与记录

记录修改前后的版本、样本量、评测规则、执行方式和结果。区分：

- `observed`：实际运行或人工审查观察到；
- `static`：结构或文本检查；
- `estimated`：有明确计算方法的估计；
- `missing`：尚未获得证据。

改进历史只记录可追溯的变更和证据链接。没有可复现实验时，不填写“准确率提升”“输出减少”等百分比。

`scripts/improve.py` 只生成提案，不修改目标；`scripts/ye.py improve` 也遵守同一边界。不要引用不存在的 `diagnose.py` 或未实现的自动补丁能力。
