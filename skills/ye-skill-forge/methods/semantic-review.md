# 语义审查

结构校验说明文件可读，语义审查判断方法能否达成用户结果。由当前 Agent 阅读入口、按需引用、代码和代表性材料执行审查；CLI 的标题、字段和案例检查不替代此步骤。

## 沿任务检查

选择正常请求、缺失输入和最近的失败或近邻请求，逐步推演：

| 检查 | 要找的具体问题 |
| --- | --- |
| 职责与路由 | 合法任务被排除，相邻任务被误接，新增功能改变了原职责 |
| 决策 | 规则相互矛盾，“深入/完整”等要求没有可执行判断，例子违背正文 |
| 输入与前置条件 | 输入不存在却直接进入下一阶段，缺字段时没有询问或降级策略 |
| 资源 | 文件可读但入口没有加载条件，相对路径按错文件解释，脚本依赖未说明 |
| 交接 | 上一步输出不能满足下一步必需输入，失败后仍假装继续，状态和来源丢失 |
| 完成与证据 | 产物存在被当作质量通过，推测被写成已观察事实，待审结果计入成功 |
| 成本与维护 | 重复读取、重复规则、无收益的固定报告或角色，过期平台和工具假设 |

没有执行环境时只做推演，标为假设或静态发现；有权限和环境时用实际输入复现。无需为了审查默认启动多个 Agent。

## 发现格式

每项发现记录严重度、具体请求或前置状态、对应文件位置、预期与错误行为、依据、最小修复及验证方式。先列影响用户结果或已有有效行为的错误，再列缺少证据和可选改进。没有足够依据时写待验证问题，不虚构失败。

例如：来源筛选步骤可返回空列表，但综合步骤无条件生成结论。用无合格来源的输入检查是否错误地产生结论；修复为空来源时返回缺口，保留正常来源的综合行为。此发现来自阶段契约，不来自缺少某个标题。

改进时围绕相同职责比较候选方案。只有边界、失败路径或结构取舍确实不同才需要多个方案；不为数量创建变体。
