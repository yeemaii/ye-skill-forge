# 设计筛选

Ye 借鉴成熟实践时先问三个问题：它是否改善真实决策？是否能产生可复核证据？它的成本是否与目标 skill 的风险匹配？三个问题有一个答不上来，就降级为可选建议或不纳入默认流程。

## 保留为核心

| 能力 | 保留原因 | 最小实现 |
| --- | --- | --- |
| 需求与边界建模 | 防止把一次性任务做成错误的 skill | 目标、输入、输出、非目标、成功条件 |
| 触发与输出评测 | 静态结构不能证明行为质量 | 正例、负例、近邻例、输出契约检查 |
| Skill IR | 避免不同平台各写一份而产生语义漂移 | 一个源模型，目标适配从它生成 |
| 信任与路径安全 | skill 脚本会读取文件、联网或写入 | 秘密、权限、网络、依赖、路径穿越扫描 |
| 包校验与安装模拟 | 发现归档和安装阶段的问题 | 安全 zip、临时目录解压、结构验证 |
| 升级检查 | 防止元数据和兼容性静默破坏 | semver、目标变化、迁移说明 |
| 反馈闭环 | 把真实失败转成下一次评测 | 反馈分类、提案、回归例 |

## 只在触发条件满足时启用

| 能力 | 启用条件 | 约束 |
| --- | --- | --- |
| 盲审和 A/B 输出实验 | 输出判断主观、影响大或需要独立审查 | 不把待审样例算作通过 |
| 权限审批与发布锁 | 网络、子进程、敏感数据、高权限写入或外部发布 | 审批需有范围、原因、期限和证据 |
| 注册审计 | 团队共享、版本分发或可安装归档 | 本地个人 skill 不要求注册表 |
| 遥测与漂移 | 有真实重复使用且能遵守本地最小化隐私规则 | 只收元数据，不扫描私有日志，不把无数据当通过 |
| Skill Atlas | 同一工作区有多个会互相竞争的 skill | 只输出组合层面的路由冲突 |
| 多平台编译 | 用户明确要跨客户端交付 | 编译成功不等于目标客户端运行时兼容 |

## 不作为默认门禁

- “世界级”或公共基准声明：没有外部、模型执行或人工证据时只能写证据计划。
- 多个内容相同的 HTML/Markdown 报告：保留一个机器可读报告和一个必要的人读摘要。
- 原生客户端遥测桥接：需要真实客户端安装和维护，不能用生成 hook 代替运行证据。
- 仅为提高分数的描述优化：如果没有实际误触发/漏触发案例，不改写触发词。
- 自动自我修改：先生成提案，经过授权和回归检查后才写入。

## 选择输出

每次审查都应写出：选了哪些门禁、为什么选、跳过了哪些门禁、为什么跳过、哪些结论仍为“缺少证据”。这样可以保持可审计性，又不会把流程复杂度误当作质量。
